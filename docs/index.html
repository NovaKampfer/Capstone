01 / Reflection

Professional Self-Assessment

My computer science work has moved from getting individual features to run toward building software whose design, behavior and limits I can explain. MultiTasked brings that growth together in one Kotlin Android application. Its three enhancements connect interface architecture, task-ordering algorithms and persistent data. Using one evolving artifact made me consider how a decision in one layer affects the others.

My career reflection identifies junior Android developer, mobile developer and entry-level software engineer roles as my immediate direction. I am most engaged by the cycle of designing a feature, implementing it, testing it and seeing the result in an application. My interest in security informs that direction through attention to validation, access boundaries and privacy. I want to continue building applications and gaining professional experience before deciding whether further education or a targeted certification best supports my next step.

A strength I developed is improving an existing design without discarding useful work. MultiTasked already had MVVM, repositories, dependency injection and reactive state. The software-design enhancement made those boundaries clearer through a typed action contract, smaller composables and a narrow settings interface. I learned that testability often improves when a production dependency becomes more precise. I also learned to preserve coroutine cancellation and to show success feedback only after a write succeeds.

The algorithms enhancement strengthened my ability to turn an ambiguous product request into a precise, testable rule. “Urgency” needed an order for incomplete work, overdue dates, priority and ties. Implementing stable merge sort and a binary heap made their costs concrete. Both full-list approaches remain O(n log n); a custom implementation is valuable here as evidence of understanding, while a library solution would usually reduce maintenance. The database enhancement extended that reasoning to foreign keys, transactions, derived counts and migrations.

Communication is part of the implementation. My narratives explain the original problem, the change and the trade-offs; source links and test records let another reader inspect the evidence. My instructor’s request to remove distracting template material guided this portfolio’s essay-style presentation. Positive milestone feedback helped confirm the category boundaries. I rerecorded the original-code walkthrough in response to the microphone and upload feedback, and the portfolio now includes that recording with direct public access. This is a real feedback loop, but I do not treat a repository or solo project as proof of professional team collaboration. I still need stronger examples of shared decision making with peers and diverse stakeholders.

Security awareness also means naming the boundary of a claim. Input validation and parameterized queries help protect data integrity. They do not encrypt Room or separate local boards by Firebase account. The local workspace belongs to the app installation; shared boards use a separate cloud path with authorization assumptions that still need testing. Publishing a portfolio adds another responsibility: keep private configuration, signing material and user data out of downloadable sources.

The final preparation produced new evidence: an Android build, 49 passing unit tests, 11 passing instrumentation tests including ten Room checks, and 11 supplemental SQLite checks. Correcting two test assumptions reinforced why historical success is not enough to validate a later version. These results support my technical growth while leaving clear next steps: verify shared Firebase interactions and broaden user-interface testing. My aim is to be a developer who can explain both why a solution works and what evidence is still needed.

03 / Clearer boundaries

Software Design and Engineering

MultiTasked already used Kotlin, Jetpack Compose, MVVM, StateFlow, Hilt and Firebase. The problem was concentrated responsibility: one board-detail file mixed lifecycle collection, rendering, editing controls and feedback. Recent sorting also relied on document IDs rather than creation timestamps.

I made the feature’s boundaries explicit. A typed action contract describes user intent; the route connects the ViewModel and lifecycle; focused composables render state. Validation and a shared coroutine helper make failures more predictable, and celebration follows a successful repository write.

BoardDetailContract.ktBoardDetailScreen.ktBoardDetailViewModel.ktCelebrationSettings interface

Skills and trade-offs. Unidirectional state, interface segregation and lifecycle-aware collection improve testability, at the cost of more small files and an explicit action model. I learned to preserve sound architecture while refining its boundaries. Extracting TaskSortPolicy was a correctness/design step; the custom algorithms belong to the next milestone.

Verification. The corrected narrative reports a successful Milestone Two Android Studio build and unit tests. The final cumulative copy now passes 49 unit tests, including six ViewModel tests. Firebase-backed interactions and the celebration flow still need end-to-end checking. Outcomes 2, 4 and 5 are the strongest alignment; reviewer-facing contracts support Outcome 1 without proving team collaboration.

04 / Explicit ordering rules

Algorithms and Data Structures

The software-design snapshot supported Recent, Alphabetical and Incomplete first. It did not express the more useful questions “Which deadline is next?” and “Which task is most urgent?” I added explicit ordering rules and tested those rules independently of the interface.

Due date · stable merge sort

Earlier dates first, missing dates last, then priority. Exact ties preserve input order because the merge takes the left element on equality.

O(n log n) time · O(n) auxiliary storage plus the recursion stack.

Urgency · binary min-heap

Incomplete, overdue, priority, due date, creation time, then ID. Completed tasks are never overdue. Each sort uses one captured time.

O(1) peek · amortized O(log n) insertion · O(log n) removal.

TaskMergeSorter.ktTaskPriorityQueue.ktTaskUrgency.ktTaskSortingService.kt

Skills and trade-offs. Rebuilding and draining the queue still costs O(n log n); no measured speedup is claimed. A standard-library solution would require less maintenance. Copying mutable tasks protects heap ordering, and cancellation avoids spending CPU on obsolete results. An injected dispatcher moves sorting off the main thread; urgency refreshes every 60 seconds while observed.

Learning and verification. “Urgency” became testable only after defining its precedence rules. The historical record reports 38 standalone tests; the final Android unit suite now also passes the worker-dispatch, cancellation, stability and randomized checks. Performance on a large live UI dataset remains unmeasured. This is primary evidence for Outcome 3, with support for Outcomes 2, 4 and resource-conscious reasoning in Outcome 5.

05 / Responsible persistence

Databases

The earlier application stored shared boards in Firebase and had empty local database placeholders. I implemented a separate On this device workspace with Room. Shared boards still uses Firebase. There is no Room–Firestore import or synchronization.

Boards and tasks use UUID primary keys and a required foreign key. Cascading deletion prevents orphan tasks. Bound queries scope task mutations to both board and task IDs. A transaction creates a board and its optional first task together; ABORT conflict handling avoids replacing a parent. A LEFT JOIN calculates task counts, and a boardId/createdAt index supports per-board reads.

TaskEntity.ktBoardDao.ktTaskDao.ktLocalBoardRepository.ktAppDatabase.ktLocalWorkspaceScreen.kt

Skills and trade-offs. Derived counts avoid duplicated state; an index improves reads while adding write/storage cost. The v1→v2 migration preserves a documented test fixture; no earlier shipped Room database or Firebase conversion is implied. Due-date input stores midnight UTC, which can differ from a user’s expected local deadline. I learned that persistence requires relationships, atomic operations and migration discipline—not only saving a record.

Security limits. Room is not encrypted automatically. This workspace is device-scoped, not isolated by Firebase account; sign-out does not clear it. Database backup/transfer exclusions, title limits and parameterized queries reduce specific risks but do not establish complete security. The legacy shared workspace and deployed Firestore rules still need separate authorization testing.

Verification. The final Android build and generated Room schema succeeded. Ten Room instrumentation tests now pass, covering CRUD, scoping, foreign keys, cascading deletion, rollback, validation, literal inputs, persistence and migration. Eleven supplemental SQLite checks also pass; they remain a separate layer of evidence. Outcome 4 is primary, supported by Outcomes 2, 3 and 5.
