MultiTasked Software Design and Engineering Enhancement Narrative

CS 499 Milestone Two

StudentMatthew Baerg
CourseCS 499 Computer Science Capstone
ArtifactMultiTasked Android Application

This narrative explains why I selected MultiTasked for my ePortfolio, how I strengthened its software design and engineering, which course outcomes the enhancement supports, and what I learned while improving an authentic unfinished codebase. The main result is a clearer, more testable board-detail feature that preserves the application's existing MVVM foundation while making UI responsibilities, user actions, and asynchronous error handling easier to follow.

Artifact Description

MultiTasked is an original Android task-management application written in Kotlin. The preserved source package contains files from November and December 2025; its Git history was not supplied. The application allows a user to register or sign in, create and join shared boards, add and update tasks, mark tasks as complete, assign tasks to board members, and delete tasks or boards. Grocery boards also track task prices and display a running total. Individual tasks can store notes, a due date, a priority, an assignee, and a creation timestamp.

The original application already used several modern Android tools: Jetpack Compose for the user interface, ViewModels and StateFlow for screen state, Hilt for dependency injection, Kotlin coroutines for asynchronous work, DataStore for settings, Firebase Authentication for user identity, and Cloud Firestore for shared data. For that reason, I did not describe the enhancement as introducing MVVM from the beginning. Instead, I treated the existing code as a partially implemented MVVM application whose feature boundaries and responsibilities needed to become more consistent.

Reason for Including the Artifact

I selected MultiTasked because it is substantial enough to represent real mobile software while still preserving visible weaknesses from its original development. It includes authentication, remote persistence, reactive state, navigation, dependency injection, and an interactive Compose interface. At the same time, the board-detail screen combined lifecycle collection, ViewModel calls, navigation, temporary UI state, task-list rendering, editing controls, loading and error states, and a celebration effect in one large file. This made the artifact a useful demonstration of my ability to review my own work honestly and improve it without discarding the functioning architecture.

The artifact also supports the larger ePortfolio plan. Its task model already contains creation time, due date, priority, and completion information that can support the later algorithms and data structures enhancement. Its empty Room files provide an authentic starting point for the later database enhancement. Keeping all three enhancements in one application will show how architecture, algorithms, persistence, testing, and security decisions affect the same product over time.

How the Artifact Was Improved

The main design change was to give the board-detail feature an explicit contract. BoardDetailContract now contains the immutable BoardDetailUiState, the available sorting choices, and a sealed BoardDetailAction hierarchy. The Compose layer sends actions such as AddTask, ToggleTask, SortChanged, or Retry instead of calling many unrelated ViewModel methods. This creates a single input boundary and makes the direction of data flow visible: the screen renders state, the user produces an action, the ViewModel applies the rule or calls the repository, and updated state returns to the screen.

I separated BoardDetailRoute from BoardDetailScreen. The route owns lifecycle-aware StateFlow collection, Snackbar side effects, and the ViewModel connection. The screen receives plain state and callbacks, so its rendering can be reasoned about without a repository or Android lifecycle. I also divided the interface into focused composables for the top bar, new-task controls, loading state, error state, progress display, task list, and task row. TaskRow and its editor moved into a separate file. At widths of 600 dp or greater, the add-task field and button use a horizontal arrangement; on compact screens they remain stacked. This is a small but concrete responsive design improvement that does not require maintaining two screens.

The ViewModel now validates blank task titles, nonfinite or negative prices, and blank assignee identifiers before the repository is called. Repeated coroutine try-and-catch blocks were replaced with one launchRepositoryAction helper. The helper rethrows CancellationException so cancellation continues to work as intended. It displays a stable, user-appropriate error message and records only the exception type instead of sending a potentially sensitive backend message to the user or error collection. I also moved the celebration state change until after the repository update succeeds, which prevents success feedback when a write fails.

I extracted the existing sort choices into TaskSortPolicy so they are independent of the ViewModel and directly testable. This is not the custom sorting algorithm planned for the algorithms and data structures milestone; it is a design separation and correctness repair. The original Recent option sorted by Firestore document ID, even though the TaskItem model already stored createdAt. The enhanced policy sorts by createdAt and applies deterministic tie breakers. Finally, I confirmed with a project-wide reference search that the duplicate com.baerg UserRepository file had no usages and removed that ghost code from the enhanced version.

Course Outcome Coverage

This enhancement substantially advances Outcomes 2, 4, and 5. It also makes partial progress toward Outcomes 1 and 3 without replacing the larger enhancements planned for later milestones.

Outcome 2 Professional communication. The feature contract, focused file organization, KDoc, change summary, unit-test names, and this narrative communicate the design to technical and nontechnical audiences. The code now tells a clearer story from user action to state update.

Outcome 4 Computing techniques and tools. The enhancement applies Kotlin sealed interfaces, MVVM, unidirectional data flow, lifecycle-aware Compose state collection, Hilt dependency injection, coroutines, responsive Compose layout, repository boundaries, and automated tests to deliver a more maintainable feature.

Outcome 5 Security mindset. Validation now occurs in the ViewModel rather than relying only on disabled UI controls. Generic user messages and error-type-only logging reduce unnecessary exposure of implementation details. Preserving coroutine cancellation also avoids treating normal lifecycle cancellation as an application failure.

Outcome 3 Algorithmic solution design. Moving sort behavior into a deterministic policy and testing the creation-time rule demonstrates a small amount of algorithmic reasoning. The planned priority queue, custom stable sort, complexity analysis, and background dispatcher remain reserved for the algorithms and data structures enhancement so the milestones stay distinct.

Outcome 1 Collaboration and decision making. The explicit contract and file-by-file enhancement notes make responsibilities and tradeoffs easier for another developer or reviewer to evaluate. A future iteration could strengthen this outcome through peer review evidence and documented feedback.

Reflection on the Enhancement Process

The most important lesson was that refactoring is not the same as replacing code. The original application already had useful MVVM, repository, Flow, and dependency-injection decisions. My task was to preserve that working direction while making the boundaries more visible. Introducing a sealed action contract helped me see that a screen does not need a separate public ViewModel method for every control. The contract makes user intent explicit and gives the ViewModel one entry point without moving business logic back into Compose.

A second lesson involved dependency size. BoardDetailViewModel needed only one setting, but it depended on a concrete SettingsRepository backed by Android Context and DataStore. Adding the narrow CelebrationSettings interface made the dependency honest and made local testing practical. This was a useful example of the interface-segregation principle: testability improved because the production dependency became smaller and clearer, not because test-specific logic was inserted into the ViewModel.

The error path was the most subtle challenge. A shared helper reduced repeated code, but it also had to preserve coroutine cancellation and avoid allowing a logging failure to hide the original user message. I learned to treat CancellationException separately, set the stable UI message first, and make remote logging best effort. I also moved the celebration trigger until after a successful repository write. That small ordering decision prevents the interface from claiming success before the data layer confirms it.

I also had to manage scope. It would have been easy to add Room, a priority queue, or a custom sort while editing this feature, but doing so would blur the evidence for later categories and make this enhancement harder to explain. I therefore limited the sorting change to fixing the incorrect key and separating the policy. The full custom algorithm and database work remain later milestones. This decision improved the clarity of both the code and the ePortfolio narrative.

I verified the enhanced project in Android Studio. The assembleDebug task completed successfully after executing 43 tasks. The only compile messages were two nonblocking deprecation warnings in BoardsScreen identifying Divider for eventual replacement by HorizontalDivider. I then ran testDebugUnitTest, and Gradle completed successfully with no failed tests. This was my reported evidence of compilation and unit-test execution for Milestone Two; it was not an emulator or Firebase integration test. Manual testing of Firebase-backed interactions remains a separate integration check because it depends on device, network, and account state.

Conclusion

This enhancement makes MultiTasked a stronger software-design artifact because the board-detail feature now has an explicit contract, clearer responsibility boundaries, safer asynchronous error handling, responsive Compose behavior, and meaningful tests. The work demonstrates that I can evaluate an imperfect application, preserve sound existing choices, and make focused improvements whose benefits can be explained and verified. It also leaves a cleaner foundation for the planned algorithms and database enhancements.
