MultiTasked Database Enhancement

Matthew Baerg · CS 499 Milestone Four · October 6, 2026

Artifact and reason for selection

MultiTasked is my Kotlin Android application for organizing tasks within boards. The original source archive contains files dated November and December 2025. The database enhancement was prepared in October 2026, building on the software design and algorithms enhancements from earlier CS 499 milestones. The submission includes the original project, the Milestone Three baseline, and the current enhanced code.

I selected this artifact because it connects database design to a practical application. A task manager needs to preserve records, associate each task with the correct board, and reflect edits consistently. Those requirements let me demonstrate relational modeling, queries, transactions, and data integrity within a working application structure. They also give the ePortfolio a continuous example of improvements across all three enhancement categories.

The original plan called for local Room storage and full CRUD operations. Inspection of the actual baseline showed that shared boards already used Firebase and that six local database files were empty placeholders. The enhancement implements those local files and adds an On this device workspace. Existing Firebase boards remain available through Shared boards. This delivers local Room CRUD without claiming to import or synchronize Firestore data. Retaining the cloud workspace is a scope clarification to discuss with my instructor if the approved plan requires a complete replacement of Firebase.

Database implementation and improvements

The local schema contains boards and tasks linked through a required foreign key. Each record has a UUID primary key. A task cannot reference a missing board, and deleting a board cascades to its tasks. Board counts are calculated with a LEFT JOIN and COUNT rather than stored as a second value that could become inconsistent. An index beginning with boardId supports task queries within a board.

The DAOs provide create, read, update, and delete operations using bound SQL parameters. Repository validation rejects blank or oversized titles, and task edits check both board and task identifiers. Creating a board with an optional first task uses one transaction: either both inserts succeed or neither remains. Inserts use ABORT on conflicts to avoid replacing a parent record and unintentionally removing its children. Room provides the entity, DAO, and database structure used for this implementation (Google, n.d.-a).

Persistence and integration

The local workspace lets a user create and rename boards, add and edit tasks, mark them complete, and confirm deletions. Dates and priorities are saved with the task records. Coroutine DAO methods and observable Flow queries connect persistent data to the ViewModel. The interface closes an editor only after a successful write and keeps its entered values available when a write fails. The Milestone Three sorting service is reused for Recent, Due date, and Urgency ordering.

The database is versioned, with a non-destructive migration from an explicit version-one test schema to version two. The migration adds notes, due date, and priority while preserving existing rows. Defaults provide valid values for old records. The earlier application did not have an active Room database, so this migration demonstrates local schema evolution rather than a conversion of existing Firebase records. The configuration requests a generated schema export and avoids destructive migration fallback. Google’s migration guidance informs the emphasis on preserving stored data across version changes (Google, n.d.-b).

Course outcomes and coverage

Outcome 4 is the primary focus: applying established computing tools and techniques to deliver useful software. Room entities, DAOs, repository integration, and the local workspace provide direct evidence of database implementation. Outcome 3 is also supported through design tradeoffs, including the index’s read benefit and write cost, derived counts instead of duplicate state, and the choice to keep local and shared storage separate rather than introduce an untested synchronization system.

Outcome 5 is supported by parameterized queries, input validation, explicit foreign-key constraints, and database exclusions in Android backup and device-transfer rules. These measures have limits. The local workspace is device-scoped and available to anyone using the same app installation. Room does not encrypt the database, and the new data is not isolated by Firebase account. Stronger protections would be needed for sensitive records. The implementation therefore demonstrates progress toward a security mindset without claiming complete security coverage.

Outcome 2 is supported by this narrative, the database walkthrough, and the documented test scope. Outcome 1 still requires evidence of collaboration, including instructor discussion and incorporating feedback. My outcome-coverage plan continues to emphasize database implementation for Outcome 4, supported by design evaluation and security reasoning. I will use feedback on the storage scope and testing results when polishing the final ePortfolio.

Reflection and validation

The central lesson in this enhancement is that persistence includes responsibility for consistency. Saving a task is only one part of the problem. The database must also prevent orphan rows, preserve relationships during deletion, and retain existing information when the schema changes. The optional first-task operation makes the value of a transaction concrete: a partially created board should not remain when a related insert fails.

Another challenge is distinguishing local storage from synchronization. Adding Room does not automatically make it a synchronized copy of Firebase. The explicit workspace choice makes the behavior understandable and avoids silently creating conflicting records. The date field also requires a clear convention: the current editor stores midnight UTC, which is deterministic but may differ from a user’s expectation of a local end-of-day deadline. Those tradeoffs are useful points for further product review.

Verification produced 43 passing JVM tests, including the existing algorithm tests and five new date-input tests. The database Kotlin classes type-check against official Room APIs. Eleven additional SQLite checks passed using query and migration strings extracted from the actual Kotlin files. They cover CRUD, board scoping, foreign keys, cascades, rollback, derived counts, literal input handling, index use, migration preservation, and persistence after reopening a database file.

Full Android validation remains outstanding. The Gradle distribution download failed in the preparation environment, which also lacks an Android SDK. Room annotation processing, generated schema validation, Hilt and Compose integration, and emulator behavior have not been verified for this version. Ten Room instrumentation tests are included to check the real generated database implementation, including persistence and migration. The passing SQLite checks do not substitute for those tests. The README provides the commands and manual steps needed to complete that verification.

AI assistance was used to prepare the code and documentation. My next responsibility is to work through the file-by-file guide, run the Android checks, and ensure that I can explain the implementation and its limits. The preserved baseline makes each change reviewable. Instructor feedback will guide final revisions before the artifact is published in my ePortfolio.
