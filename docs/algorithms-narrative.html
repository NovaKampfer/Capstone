MultiTasked Algorithms and Data Structures Enhancement

Matthew Baerg · CS 499 Milestone Three Narrative · September 27, 2026

Artifact and purpose

MultiTasked is my Kotlin Android task-management application. It organizes tasks within boards and includes task details such as completion status, priority, and due date. The original project archive contains source files dated November and December 2025. This algorithms enhancement was prepared in September 2026 and builds on the separate software design enhancement from Milestone Two.

I selected MultiTasked for my ePortfolio because it connects algorithm choices to a practical user need: deciding which task to work on next. The earlier task-list sorting policy supported recent, alphabetical, and completion-based ordering, but did not provide the planned due-date and urgency ordering. The enhanced version adds both choices while retaining the existing application structure and Firebase data layer. The ZIP preserves the original code and the Milestone Two baseline so the changes can be compared directly.

Enhancement and design choices

The Due date option uses a custom stable merge sort. It compares due dates first, places tasks without a date after dated tasks, and uses priority when dates tie. When both keys are equal, merge sort preserves the input order. The implementation divides the list into smaller ranges, sorts each half, and merges the results. Choosing the left item when keys compare equally is the specific decision that makes the algorithm stable.

The Urgency option uses a custom array-backed binary min-heap. Tasks are ordered by completion status, overdue status, priority, due date, creation time, and ID, in that sequence. Incomplete tasks come first. Among them, overdue tasks come before upcoming tasks, even when an upcoming task has a higher priority. Completed tasks are never classified as overdue. Missing dates are placed last within the preceding rule groups. These explicit rules make the result explainable and testable.

Merge sort takes O(n log n) time and O(n) auxiliary space, with an additional O(log n) recursion stack. The heap provides O(1) peek, O(log n) removal, and amortized O(log n) insertion. Rebuilding and draining the heap for a full task list still takes O(n log n), so I do not claim that it is asymptotically faster than merge sort. The heap demonstrates priority-queue behavior; a future scheduler could use it to retrieve the next task repeatedly. A standard library implementation would generally require less maintenance outside the capstone learning context.

Background work and application integration

TaskSortingService moves the CPU work into an injected coroutine dispatcher, supplied as Dispatchers.Default in the application. Declaring a function suspend would not accomplish that by itself; withContext performs the context switch. The service copies task values before sorting, and the algorithms check cancellation during their loops. When new task data or a new option arrives, the flow pipeline cancels superseded work. The sorted list travels with its selected option so the displayed label corresponds to the result.

Urgency depends on time, even when no task is edited. The service therefore refreshes the captured timestamp every 60 seconds while its urgency flow is observed. Each individual sort uses one fixed timestamp so its comparator remains consistent. An injected clock makes this behavior testable without waiting for real deadlines. The existing screen receives the results through the ViewModel and exposes the two new choices in its sorting menu. Google’s coroutine guidance supports injecting dispatchers and making blocking or CPU-intensive operations safe to call from the main thread (Google, n.d.).

Reflection and verification

The most important learning focus for me is the relationship between an algorithm and the rules it is supposed to implement. “Sort by urgency” is not precise enough to test. Deciding how overdue work, priority, missing dates, and completed tasks interact produces an ordering contract that can be checked. Stability is similarly specific: preserving equal-key order depends on a comparison branch in the merge operation, not merely on calling an algorithm stable.

The implementation also exposes challenges that are easy to overlook in a small demonstration. A heap can lose its ordering invariant if a caller changes a stored task’s priority fields. The queue therefore copies tasks when they enter and leave it. A background coroutine can continue consuming CPU after it is no longer useful unless its computation cooperates with cancellation. Kotlin’s ensureActive API provides an explicit cancellation check for this kind of non-suspending work (JetBrains, n.d.). These details are important study points as I work toward explaining every line of the enhancement.

The supplied verification record reports 38 passing JUnit tests across six suites, compiled from the actual production algorithm, model, policy, and coroutine-service sources. Coverage includes empty lists, duplicates, stable ties, extreme and missing dates, randomized heap operations, comparison-count bounds, worker-thread execution, and cancellation. The randomized tests use fixed seeds for repeatability. Operation-count checks support the complexity discussion; they are not measurements of a faster Android interface.

The full Android build has not been verified for this version in the preparation environment, which lacks the Android SDK and could not complete the Gradle wrapper download. The six ViewModel tests, Hilt generation, Compose integration, and emulator behavior therefore remain local validation steps. Earlier Milestone Two build results do not establish that these new changes work. Before describing the application as fully tested, I need a successful Android build and test report and a manual check of both new sorting options. The package README records those steps and the exact scope of the passing tests.
